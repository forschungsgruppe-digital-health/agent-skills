# AGENTS.md — working in this repository

Operating guide for an agent working **on this catalog**. This is not about the skills it
contains; for authoring one, read `CONTRIBUTING.md` or load the `skill-authoring` skill.

## What this repository is

An organization-wide catalog of Agent Skills conforming to the open standard at
<https://agentskills.io/specification>. Static by design: a Git repository with a generated index,
no server, no runtime. It must keep working with nobody maintaining it.

## Never edit these by hand

- **`skills/index.json`** and **`CATALOG.md`** are generated by `scripts/build_index.py`. CI
  regenerates them and fails if the working tree changes, so a hand edit is caught — but it wastes
  a review cycle.
- **`CHANGELOG.md`**, **`version.txt`**, and the `version` field inside `skills/index.json` are
  owned by Release Please. `build_index.py` reads that field and writes it back unchanged; do not
  make it compute the version, or `--check` stops being a drift test.
- **`LICENSE`** and **`LICENSE-docs`** are verbatim upstream texts.

## Adding a skill

```bash
cp -R templates/SKILL.md.template skills/<name>/SKILL.md   # then fill it in
python scripts/build_index.py                              # regenerate
git add skills/<name> skills/index.json CATALOG.md CODEOWNERS
```

Add the `CODEOWNERS` line for the new directory in the same change, matching `fgdh.owner`.

## Validation

```bash
python scripts/build_index.py --check   # catalog contract + generated-artefact drift
python scripts/check_descriptions.py    # trigger collisions between descriptions
agentskills validate skills/<name>      # specification conformance
```

Exit codes: `0` clean, `1` violation or drift, `2` the tool broke. `build_index.py` reports *all*
violations at once with stable, greppable rule names (`tier/rejected`, `name/directory`,
`path/absolute`, `mirror/experimental-banner`, …).

Note the CLI name: the PyPI package is `skills-ref`, but the console script it installs is
`agentskills`. Both the specification page and the upstream `pyproject.toml` say otherwise; the
installed artifact is the authority.

`build_index.py` must stay **deterministic and offline**. No timestamps, no network, no iteration
over an unordered set. Owner resolution lives in `scripts/check_owners.py` and runs weekly, because
a merge must not depend on GitHub's availability.

## The tier rule

`fgdh.tier` is `universal` or `domain`. **`project` is never a stored value** — such a skill
belongs in the consuming repository. When you hit `tier/rejected`, the fix is to lift the skill to
`domain` by replacing hard-coded paths with a discovery step plus an explicit failure branch, or to
move it out. Never just change the value.

## Status is invisible to agents unless mirrored

An agent sees only `name` and `description` before deciding to activate a skill. Nothing under
`fgdh.*` reaches it. So: `experimental` goes in a body banner and **not** in the description
(caution must not suppress triggering); `deprecated` **must** appear in the description (the
redirect has to arrive before the activation decision). CI enforces both directions. Exact wording
is in `CONTRIBUTING.md`.

## Commits and branching

- Trunk-based: `main` only, short-lived branches, squash merges, branch deleted on merge.
- **The pull request title becomes the commit on `main`** and is what Release Please parses. It
  must be a Conventional Commit; CI lints it. Types: `feat`, `fix`, `docs`, `refactor`, `test`,
  `chore`, `perf`, `build`, `ci`, `style`, `revert`.
- Incomplete work is merged as `experimental` with `TODO(owner):` markers, never parked on a
  branch.
- A skill removal is a two-release process. Never delete a skill folder in the same change that
  deprecates it.

## Three traps

**The pull request body becomes the commit body.** Merges are squash merges, and Release Please
runs the Conventional Commits parser over the whole message. A line in the body that looks like
`feat!: something` is read as a second commit and corrupts the generated changelog -- it happened in
v0.5.0. Never let `<type>:` or `<type>!:` begin a line in a body you write; the parser is not a
Markdown renderer, so backticks around the token protect nothing. CI rejects it now. State the
change classification in prose and let the title's type carry the machine-readable signal.


**The `grep` for path portability is substring-based.** `grep -rnE '\]\(/|\.\./' skills/` cannot
tell a violation from prose *documenting* the rule, so write "traverse upward with `..`" rather
than the two-character sequence when explaining it inside a skill. The real gate is the link-aware
`path/traversal` rule in `build_index.py`.

**Do not add a required status check in the same change that creates the job.** Requiring a check
that has never reported blocks every merge, including that one.
